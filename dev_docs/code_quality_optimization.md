# Workflow Tool 代码质量优化文档

## 1. 背景

本文档基于当前项目代码审查结果整理，目标是将现阶段已经识别出的关键质量问题转化为一份可执行的优化清单。

本轮问题主要集中在以下几个方向：

- 持久化链路中的竞态与状态一致性
- 远端文档加载失败后的错误处理
- 版本历史操作的交互正确性
- 图列表搜索与分页的请求并发安全
- 远端导入流程的审计性与版本链完整性

## 2. 优化目标

优化工作应优先保证以下目标：

- 避免用户数据被旧的 autosave 静默覆盖
- 避免错误 `diagramId` 或远端加载失败时用户误以为自己在编辑真实远端文档
- 保证版本保存与恢复的交互符合用户预期
- 保证图列表和搜索结果稳定，不受请求返回顺序影响
- 保证远端导入进入正式版本链，而不是绕过历史记录

## 3. 发现清单

### P1. Pending autosave 可能覆盖新版本

位置：

- `app/src/storage/persistenceService.ts:260-330`

问题描述：

- `scheduleAutosave()` 会把待保存草稿保存在内存中
- `saveRevision()` 和 `restoreRevision()` 执行前没有清空或处理这批 pending autosave
- 如果用户在 autosave 的 debounce 窗口内手动保存版本或恢复版本，旧草稿可能在后续继续提交
- 由于 `latestVersion` 已经变化，旧草稿会以“新版本”的身份提交，造成刚保存/刚恢复的状态被静默覆盖

风险等级：

- 高

影响：

- 可能直接破坏版本历史的可信度
- 可能导致用户误以为恢复成功，实际又被旧状态覆盖
- 属于数据一致性问题，应优先处理

建议修复：

1. 在 `saveRevision()`、`restoreRevision()`、`importDiagram()` 前统一调用一个内部方法，取消当前 pending autosave 和定时器。
2. 更稳妥的做法是增加 `flushOrDiscardPendingSave()`，支持两种策略：
   - 强制丢弃旧 autosave
   - 或在执行关键操作前先显式 flush
3. 所有会生成新版本号的操作都应进入同一“事务式持久化入口”，避免各自处理状态。

建议验收标准：

- 在 autosave 倒计时内点击“保存版本”后，不会再有旧草稿覆盖新版本
- 在 autosave 倒计时内点击“恢复版本”后，恢复结果稳定，不会被旧状态反写

### P2. 远端加载失败被静默降级为本地模式

位置：

- `app/src/storage/persistenceService.ts:119-156`

问题描述：

- `load()` 当前把远端 `404`、`401/403`、`500` 和网络错误统一吞掉
- 然后直接回退到本地缓存或默认图
- 用户可能在错误的 `diagramId`、已删除文档或无权限文档上继续编辑，却没有明显提示

风险等级：

- 中高

影响：

- 用户会误判当前文档状态
- 后续保存失败才暴露问题，排查成本高
- 远端模式与本地模式边界不清晰

建议修复：

1. 对远端错误类型做分类处理：
   - `404`：文档不存在
   - `401/403`：无权限或未登录
   - `5xx`：服务端异常
   - 网络失败：离线或服务不可达
2. 如果 URL 明确带 `diagramId`，默认应优先提示错误，而不是直接静默回退。
3. 将 `PersistenceLoadResult` 扩展为更细粒度状态，例如：
   - `server`
   - `local-cache`
   - `empty`
   - `remote-error`
4. 在 UI 中给出阻断式提示或明确的只读/离线说明。

建议验收标准：

- 输入错误 `diagramId` 时，页面应明确提示“文档不存在”
- 无权限时，不应假装成功进入本地编辑态

### P2. 取消版本说明弹窗仍会创建版本

位置：

- `app/src/App.tsx:447-458`

问题描述：

- `window.prompt()` 返回 `null` 时被 `?? ''` 转为空字符串
- 这意味着用户点击“取消”，仍会执行 `saveRevision()`
- 最终会意外创建一个没有说明的版本

风险等级：

- 中

影响：

- 用户操作语义不正确
- 容易产生无意义版本

建议修复：

1. 在 `prompt()` 返回 `null` 时直接 `return`
2. 如果后续改为自定义 modal，同样应显式区分“取消”和“提交空说明”

建议验收标准：

- 点击“取消”后，不会创建新 revision
- 点击“确认”但说明留空时，允许创建 revision

### P3. 图列表搜索结果存在并发覆盖风险

位置：

- `app/src/App.tsx:401-425`

问题描述：

- 图列表搜索使用 debounce，但没有请求取消
- 较慢返回的旧请求可能覆盖较新的搜索结果
- `loadDiagramList()` 会直接 `setLibraryMode('diagrams')`
- 如果用户在请求未返回前关闭面板，旧请求完成后还可能把面板重新打开

风险等级：

- 中

影响：

- 搜索体验不稳定
- UI 状态可能“闪回”

建议修复：

1. 为图列表请求增加 `AbortController`
2. 或使用自增请求序号，仅应用最后一次请求结果
3. 将“打开面板”与“更新搜索结果”解耦：
   - 只在主动打开图列表时设置 `libraryMode`
   - 搜索请求返回时仅更新数据
4. 对版本历史分页也可采用同样策略，保持一致性

建议验收标准：

- 快速输入多个关键词时，只显示最后一次搜索结果
- 面板关闭后，旧请求返回不会重新打开面板

### P3. 远端 JSON 导入绕过正式导入链路

位置：

- `app/src/App.tsx:533-545`

问题描述：

- 当前远端模式下导入 JSON 只是本地 `setDiagram()`
- 后续依赖普通 draft autosave 写回数据库
- 没有生成 `source=import` 的 revision
- 也没有进入专门的远端导入路径

风险等级：

- 中

影响：

- 审计性不足
- 无法区分“用户普通编辑”和“外部 JSON 导入”
- 版本链不完整

建议修复：

1. 在远端模式下导入 JSON 时，调用 `persistenceService.importDiagram()`
2. 后端补齐 `/api/diagrams/:id/import`
3. 服务端应写入一条 `source=import` revision
4. 导入失败应返回结构化错误，而不是仅在前端本地报错

建议验收标准：

- 远端导入后，版本历史中可看到 `source=import`
- 导入结构非法时，后端与前端都会明确提示失败

## 4. 优先级排序

建议按以下顺序执行：

1. 修复 pending autosave 覆盖新版本问题
2. 修复远端加载失败被静默回退的问题
3. 修复取消版本弹窗仍创建版本的问题
4. 为图列表搜索增加并发保护
5. 打通远端导入正式链路

原因：

- 前两项属于数据正确性与模式判断问题，优先级最高
- 第三项属于交互正确性问题，改动小、收益高
- 第四项主要影响稳定性和体验
- 第五项影响审计链和版本完整性，适合在前面稳定后接入

## 5. 推荐实施方案

### 阶段一：一致性修复

- 在 `PersistenceService` 中增加统一的 pending autosave 清理逻辑
- 在 `saveRevision()` / `restoreRevision()` / `importDiagram()` 前调用
- 为 `load()` 区分远端错误类型，避免无提示降级
- 修复 revision prompt 的取消逻辑

### 阶段二：稳定性修复

- 给图列表搜索与分页增加 `AbortController` 或请求序号保护
- 将图列表面板的打开状态与请求返回解耦

### 阶段三：版本链完善

- 接入远端导入专用 API
- 生成 `source=import` revision
- 在 UI 中区分普通保存、恢复版本、导入版本

## 6. 测试建议

建议补充以下自动化测试：

### 持久化层

- autosave pending 时执行 `saveRevision()` 不会覆盖新版本
- autosave pending 时执行 `restoreRevision()` 不会被旧状态反写
- 远端 `404` / `403` / `500` / network error 时返回不同加载状态

### 前端交互层

- 取消 revision prompt 不会创建版本
- 图列表搜索快速输入时仅显示最后一次结果
- 关闭图列表后旧请求返回不会重新打开面板

### 接口层

- 远端导入会生成 `source=import` revision
- 恢复版本后 `latestVersion` 正常递增

## 7. 结论

当前项目的功能链路已经基本成型，但在持久化一致性、远端错误处理和版本链完整性上仍存在几个明确风险点。

从优化顺序看，应先处理“数据不会被悄悄写坏”这类问题，再优化远端模式体验与审计链。这样可以在不大改架构的前提下，显著提升当前版本的稳定性和可维护性。
