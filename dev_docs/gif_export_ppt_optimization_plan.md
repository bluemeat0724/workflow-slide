# Workflow GIF 导出重构方案（PPT 展示优化）

## 1. 背景

当前项目已经具备 GIF 导出能力，但现有方案基于服务端 `@napi-rs/canvas` 手写重绘，再交给 `gifenc` 编码。该链路与编辑器页面和导出的 HTML 不共用同一套渲染源，已经出现以下问题：

- 页面、HTML、GIF 三套视觉实现并存，布局、间距、字体回退、换行策略不一致。
- 页面依赖浏览器真实排版与 SVG marker，而 GIF 依赖服务端 Canvas 手工绘制，视觉偏差不可避免。
- 当前 GIF 画面包含大量渐变、阴影、透明叠层和纹理，但 GIF 只有 256 色，量化后容易出现色带、噪点和闪烁。
- 当前动画时长 2.8s、56 帧、20fps，对 PPT 嵌入场景偏重，文件体积和观感都不理想。

本方案的目标不是让 GIF 继续逼近“编辑器截图”，而是重构出一条专门面向 PPT 展示的导出链路。

## 2. 目标与约束

### 2.1 业务目标

- 导出的 workflow GIF 可以直接插入 PowerPoint。
- 动画仅体现在连接线，节点、泳道、背景保持静态。
- 循环播放，时长可以较短，但要有清晰的节奏感。
- 在 PPT 缩放后仍具备较好的标题、节点和连线可读性。

### 2.2 强约束

- 画幅固定为 16:9。
- 输出格式优先支持 GIF。
- 视觉上允许与编辑器页面不完全一致，但必须稳定、干净、适合演示。
- 导出链路必须统一，不能继续维护“页面一套、HTML 一套、GIF 一套”的分叉状态。

### 2.3 非目标

- 本期不追求导出结果与编辑器交互态 1:1。
- 本期不处理节点拖拽、选中态、右键菜单、连接手柄等编辑器专属元素。
- 本期不做复杂镜头动画，不做节点入场动画，不做局部放大。

## 3. 方案决策

### 3.1 明确结论

现有 `app/server/render/gifExporter.mjs` 方案不建议继续演进为主方案。建议将其标记为待替换实现，新的主方案改为：

`Diagram` -> 统一导出模板 HTML -> Headless Chromium 逐帧采样 -> GIF 编码

### 3.2 为什么要推翻当前方案

- 根因不是局部 bug，而是渲染架构错误。当前方案天然要长期维护两套绘制规则。
- 浏览器负责排版、SVG、滤镜、字体回退，服务端 Canvas 无法低成本保持一致。
- GIF 对复杂视觉不友好，继续在手写 Canvas 上复刻复杂背景，投入越多，收益越差。
- 用户真实需求是“PPT 中展示效果好”，不是“把编辑器原样录成 GIF”。

## 4. 目标架构

### 4.1 总体链路

1. 前端仍提交当前 `Diagram`。
2. 服务端将 `Diagram` 传入统一的导出模板生成器，产出一份“演示态 HTML”。
3. 服务端用 Headless Chromium 打开该 HTML。
4. 通过固定尺寸视口和受控动画参数逐帧截图。
5. 对所有帧做全局调色板量化，再编码为 GIF。
6. 返回 `image/gif` 给前端下载。

### 4.2 统一渲染源

导出 HTML 必须成为 GIF 的唯一视觉源。推荐将现有 `app/src/utils/exportHtml.ts` 从“单次字符串拼接”升级为“导出模板生成器”，支持不同 profile：

- `profile: 'standalone-html'`
- `profile: 'presentation-gif'`

其中：

- `standalone-html` 保持当前单文件 HTML 导出能力。
- `presentation-gif` 用于服务端浏览器采帧，视觉规则专门针对 GIF/PPT 做简化。

### 4.3 为什么选浏览器采帧

- 浏览器本身就是当前页面和 HTML 导出的真实渲染环境。
- SVG path、marker、text layout、font fallback、CSS animation 都可直接复用。
- 同一份模板可同时服务于“导出 HTML”和“导出 GIF”，后续维护成本最低。

## 5. 演示态视觉规范

### 5.1 设计原则

- 以“投影清晰度”优先，压过“细节华丽度”。
- 以“静态主体稳定”优先，压过“画面层次感”。
- 以“低颜色复杂度”优先，压过“渐变与透明效果”。

### 5.2 建议视觉取舍

- 保留：16:9 画布、泳道、节点卡片、主题色、虚线流动、箭头。
- 弱化：背景纹理、叠层透明、边缘发光、超轻微阴影。
- 移除：编辑器容器外壳感、复杂网格、shared 节点的额外 halo、任何交互装饰。

### 5.3 背景规范

- 使用单层或双层轻渐变背景。
- 不使用高频网格纹理和条纹叠层。
- 对比度控制在投影设备上可读即可，不追求屏幕近距离观感。

### 5.4 节点规范

- 节点背景尽量不透明，避免半透明叠加后的色彩污染。
- 节点阴影减弱，边框略增强。
- 标题字号、正文字号、tag 字号为固定导出规格，不随浏览器窗口变化。
- 正文最多展示 2 到 3 行，超出部分截断或省略，避免小字发糊。

### 5.5 连线规范

- 仅连线参与动画。
- `theme` 边线宽建议 4px，`soft` 边线宽建议 3px。
- 箭头尺寸建议 10px 到 12px。
- 取消发光滤镜，改用纯色高对比线条，减少 GIF 量化噪点。

## 6. 动画规范

### 6.1 动画目标

- 让观众感知 workflow 的流向。
- 动画应短、干净、能循环，不抢主体阅读。

### 6.2 推荐参数

- 时长：1.3s 到 1.5s
- 帧率：12fps
- 总帧数：16 到 18 帧
- 循环：无限循环
- 动画内容：仅 `stroke-dashoffset` 变化

### 6.3 不建议继续沿用的参数

- 不建议继续使用 2.8s / 20fps / 56 帧。
- 该配置对 PPT 场景偏重，体积更大，视觉收益有限。

## 7. 输出规格

### 7.1 画布尺寸

提供两个固定档位：

- `standard`: 1600 x 900
- `hd`: 1920 x 1080

### 7.2 清晰度策略

- 浏览器内部按 2x device scale 渲染。
- 截图后按目标尺寸下采样，再进入 GIF 量化阶段。
- 这样可以提升线条边缘和文字采样质量。

### 7.3 文件体积控制

- 默认导出 `standard` 档位。
- `hd` 档位仅在用户明确需要更清晰画面时启用。
- 控制总帧数和背景复杂度，优先降低无意义颜色变化。

## 8. 编码策略

### 8.1 编码器选择

短期可继续使用 `gifenc`，但编码策略必须升级，不再沿用“首帧 palette + Floyd-Steinberg 抖动”的做法。

### 8.2 推荐量化策略

- 从所有帧采样像素生成全局调色板。
- 全局调色板统一应用于每一帧，避免时间轴上颜色漂移。
- 优先尝试不抖动或 ordered dithering。
- 只有在视觉验证确认必要时才启用误差扩散抖动。

### 8.3 原因

- 首帧 palette 容易丢失后续帧中的高亮和边线颜色。
- Floyd-Steinberg 在动态图上容易形成抖点闪烁。
- 对流程图这类几何图形，稳定性通常比细腻渐变更重要。

## 9. 模块改造建议

### 9.1 前端

建议调整如下：

- `app/src/utils/exportHtml.ts`
  - 重构为可配置导出模板生成器。
  - 输入增加 `profile`、`size`、`animation` 等参数。
- `app/src/App.tsx`
  - 导出 GIF 时改为提交结构化请求，而不是直接提交裸 `Diagram`。
- `app/src/api/contracts.ts`
  - 新增 `ExportGifRequest` 结构，显式描述导出 profile 和尺寸。
- `app/src/api/client.ts`
  - 更新 `exportGif()` 请求体，兼容新接口。
- `app/src/components/toolbar/Toolbar.tsx`
  - 如果需要，可增加“标准 / 高清”导出选项；若先做最小版本，可继续只有一个按钮。

### 9.2 服务端

建议新增或重构如下模块：

- `app/server/render/exportTemplate.mjs`
  - 负责统一生成导出 HTML。
- `app/server/render/presentationProfile.mjs`
  - 负责演示态视觉参数、字号、线宽、背景策略。
- `app/server/render/browserFrameCapture.mjs`
  - 负责启动 Headless Chromium、设置视口、逐帧截图。
- `app/server/render/gifEncoder.mjs`
  - 负责全局 palette 采样、量化、GIF 编码。
- `app/server/render/gifExporter.mjs`
  - 作为编排入口，内部调用上面三个模块。

### 9.3 当前旧实现处理方式

- 第一阶段允许保留旧 `gifExporter.mjs` 文件名，但内部改为新实现。
- 第二阶段删除旧 Canvas 手写渲染逻辑。
- 不建议同时长期保留“browser exporter”和“canvas exporter”双实现。

## 10. 接口设计

### 10.1 请求体

建议将 `POST /api/gif` 从“直接接收 Diagram”改为接收结构化对象：

```json
{
  "diagram": { "...": "Diagram" },
  "profile": "presentation-gif",
  "size": "standard",
  "loop": true
}
```

### 10.2 字段定义

- `diagram`: 当前 workflow 数据。
- `profile`: 当前先支持 `presentation-gif`。
- `size`: `standard` 或 `hd`。
- `loop`: 当前固定为 `true`，保留字段是为了后续兼容。

### 10.3 兼容策略

- 第一阶段后端同时兼容旧请求体和新请求体。
- 当前端切换完成后，再移除直接提交裸 `Diagram` 的兼容代码。

## 11. 推荐实施阶段

### Phase 1：统一导出模板

- 重构 `exportHtml` 生成器。
- 把 HTML 和 GIF 需要共用的布局、字体、SVG、动画参数统一到一套模板中。
- 新增 `presentation-gif` profile，但先不接 GIF 编码。

### Phase 2：演示态视觉落地

- 做减法，形成适合 GIF 的导出样式。
- 固定字号、线宽、边框、背景复杂度。
- 先保证静态 HTML 截图效果优于当前 GIF。

### Phase 3：浏览器逐帧采样

- 接入 Playwright 或同级 headless browser 方案。
- 固定 16:9 视口、device scale、动画帧推进方式。
- 输出逐帧 PNG 或 RGBA buffer。

### Phase 4：GIF 编码重建

- 改为全局调色板采样。
- 调整抖动策略。
- 输出可循环 GIF。

### Phase 5：前端接入与兼容迁移

- 前端切换到新请求体。
- 视需要增加导出尺寸选项。
- 保留原按钮交互，降低使用门槛。

### Phase 6：下线旧方案

- 删除服务端 Canvas 手写重绘逻辑。
- 清理 `@napi-rs/canvas` 相关导出依赖和冗余代码。

## 12. 验收标准

### 12.1 视觉验收

- GIF 首帧与 `presentation-gif` HTML 截图在结构和排版上基本一致。
- 连线方向、箭头方向、节点宽高、文字换行稳定。
- 文字、边线、箭头在 PPT 中缩放后仍清晰可辨。

### 12.2 动画验收

- 仅连线有动画。
- 动画循环自然，无明显卡顿。
- 不出现明显跳帧、闪烁或颜色忽明忽暗。

### 12.3 编码验收

- 背景和节点边缘无大面积脏色块。
- 不因 palette 漂移造成相邻帧色彩突变。
- 中文和英文标题都可正常显示。

### 12.4 场景验收

至少人工验证以下样例：

- 2 个泳道、3 到 5 个节点、短文本。
- 4 个泳道、8 到 12 个节点、长中文描述。
- 混合中英文标题与 tag。
- 天蓝、琥珀、石墨三套主题。

### 12.5 PPT 验收

- 插入 PowerPoint 后能正常循环。
- 在 100% 页面宽度下，标题和主要节点仍可读。
- 放映模式下不出现明显锯齿、噪点干扰和过重闪烁。

## 13. 测试建议

### 13.1 自动化测试

- 单测：导出请求体解析、尺寸映射、动画参数映射。
- 单测：全局 palette 构建和 GIF encoder 基本输出。
- 集成测试：对固定 `Diagram` 导出 GIF，断言尺寸、帧数、非空输出。

### 13.2 手工测试

- 本地导出 HTML，先看静态首帧是否满足演示需求。
- 再导出 GIF，对比首帧和 HTML 截图差异。
- 最后插入 PowerPoint 进行真实演示验证。

## 14. 风险与注意事项

- 新方案需要引入浏览器运行时，部署环境必须允许 Headless Chromium 工作。
- 字体一致性依赖导出环境中的可用字体，必要时应考虑打包或约束字体集。
- 若部署环境无法稳定运行浏览器，必须优先解决运行时问题，不能再退回 Canvas 手写重绘路线。

## 15. MVP 范围

第一版建议只交付以下能力：

- `presentation-gif` 单一 profile
- `standard` 与 `hd` 两档尺寸
- 仅连线动画
- 固定时长、固定帧率、固定循环
- 前端一个导出入口

这能最快把方案拉回到“可贴进 PPT 且观感稳定”的目标线上。
